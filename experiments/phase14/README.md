## 結論
**全面移行は推奨しない。A方式を維持し、局・日付起点の発見を補助として検証し続ける。**
Bで既存公開にない10枠を見つけた一方、既知のゴルフや釣りの確認用番組を拾い切れなかった。Bだけで全20ジャンルを網羅できる優位性は確認できない。
今回確認した情報源の中で、全ジャンルの広域番組表について「無料・継続自動取得・アプリ向け再配信」の条件を満たすものは確保できていない。既存アニメAPIは利用可能だが対象範囲が異なる。

## 1. 現行方式Aと根本原因
WorkのWeb検索 → ジャンル/定番追跡 → ai-candidates.jsonのdiscoveries → ledger.prepare/project → source_rulesの個別条件・日時・局・分類検証 → autopublishの統合/重複/矛盾/大量消失防止 → GitHub更新 → Actions検証/しょぼいカレンダー取得 → Pages → Androidキャッシュ表示。
ActionsはAI Web検索を実行しない。検証・配信の成功は、発見範囲の十分さを保証しない。

見落としの主因は、検索語と検索順位に依存し、局×日×時間帯の観測範囲/未観測範囲を管理していないこと。定番50件は既知番組を補うが、未知の特番や一般番組内の企画の発見を保証しない。
さらに、検索索引とページ本文のキャッシュ時差、次回枠と古い回の混在、取得できても継続再配信条件が未確保という別々の問題がある。発見・事実確認・分類・利用判断を同じ「掲載不可」で潰すと、改善すべき段階が見えなくなる。

## 2. B方式の構造と実施範囲
1. **ジャンル指定なし**の局・日付検索12件と、公式週間表3か所の通常閲覧を試行した。全表の機械取得や非公開エンドポイント探索はしていない。
2. 25候補を observations-b.json へ最小事実だけ独立記録。紹介文・画像・出演者一覧は保存していない。
3. Workが当該回の内容を参照し、classifications.jsonへ独自の判定根拠を作成。Pythonがタイトルの単語からジャンルを生成する仕組みではない。
4. compare.pyは候補統合、日付/局/出典/矛盾チェックと分類根拠のゲートだけを再現する。AI検索・AI分類の無人実行コードではない。
5. 0件/極少/確認リストの取りこぼしを検出し、全20ジャンルについて定番50件の関連IDを不足調査へ渡す。今回の不足補完では必須8ジャンルで実検索を8件追加した。Bの後の追跡なので、盲検のA実験として件数評価には使っていない。

対象期間は同じ7日間だが、全局×7日×全時間帯の網羅収集には成功していない。Bは限定標本である。ジャンル語への依存は減ったが、検索索引の順位と掲載範囲への依存は残る。
